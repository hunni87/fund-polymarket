# 아키텍처

계속 고쳐가며 쓸 것을 전제로 잡았다. 이 문서는 "왜 이렇게 했는지"와 "다음에 어디를
건드리면 되는지"를 남긴다.

## 레이어

```
API (FastAPI)          HTTP 경계. 권한 확인, 스키마 검증, 커밋.
  └ services/          비즈니스 규칙. DB 세션은 받지만 HTTP는 모른다.
      └ brokers/       증권사 어댑터. Protocol 하나로 추상화.
  └ models/            SQLAlchemy 테이블.
```

원칙 하나: **`services/consensus.py`는 DB도 설정도 모른다.** 확률 계산, 파리뮤추얼
정산, 판정 규칙, Brier score가 전부 순수 함수다. 돈 계산이 틀리면 안 되는 부분이라
단독으로 테스트할 수 있게 떼어놨다.

## 도메인 모델

| 테이블 | 역할 |
|---|---|
| `members` | 스터디원. `role`이 `admin`이면 운영자 액션 가능 |
| `funds` | 증권 계좌 1개 = 펀드 1개 |
| `positions` | 종목별 보유 수량. 증권사 잔고에서 동기화 |
| `markets` | 하나의 의사결정 주제. 판정 규칙과 주문 파라미터를 함께 들고 있다 |
| `bets` | `(market, member, outcome)` 당 한 행. 스테이크를 쪼개 걸 수 있다 |
| `ledger_entries` | 포인트 원장. **추가 전용** |
| `trade_decisions` | 합의 → 매매 결정. 확률 스냅샷을 함께 보관 |
| `orders` | 브로커로 나간 주문. 요청/응답 원문 포함 |

### 왜 잔고 컬럼이 없나

`members`에 `balance` 컬럼을 두지 않았다. 잔고는 항상 `ledger_entries`의 합계다.
정산 로직에 버그가 생겨도 잔고가 조용히 어긋날 수 없고, 모든 포인트 이동에 사유가
남는다. 스터디원 9명 규모에서 합계 쿼리 비용은 무시할 만하다.

부호 규약: 회원 잔고 기준이다. 베팅 잠금은 음수(`BET_LOCK`), 지급은 양수(`PAYOUT`).

### 왜 마켓 상태가 7개나 되나

`OPEN → CLOSED → DECIDED → EXECUTED → RESOLVED → SETTLED` (+ `CANCELLED`).

각 단계가 되돌릴 수 없는 부수효과와 짝지어져 있어서 합칠 수가 없다.
- `CLOSED`에서 **기준가가 확정**된다. 판정의 기준점이라 나중에 못 바꾼다.
- `EXECUTED`에서 **돈이 나간다**.
- `SETTLED`에서 **포인트가 이동한다**.

`RESOLVED`(정답 확정)와 `SETTLED`(지급)를 나눈 것은 의도적이다. 판정이 이상하면
지급 전에 사람이 확인하고 취소할 수 있어야 한다.

## 예측시장 방식: 파리뮤추얼

폴리마켓은 실제로는 CLOB(호가창) + AMM이지만, 9명짜리 스터디에는 과하다. 유동성
공급자도 없고 상시 거래도 일어나지 않는다. 그래서 **파리뮤추얼**(경마식)을 골랐다.

- 확률 = 지분 비율. 별도 가격 발견 메커니즘이 필요 없다.
- 정산 = 승자가 전체 풀을 지분대로 분배.
- 계산이 단순해서 전원이 규칙을 이해할 수 있다.

교체하고 싶다면 `services/consensus.py`의 `compute_consensus` / `settle_parimutuel`
두 함수만 바꾸면 된다. LMSR이나 시간가중 배당으로 가더라도 호출부는 그대로다.

### 정산 규칙의 디테일

- **정답에 아무도 안 걸었으면 전원 환불.** 아무도 못 맞힌 판에서 포인트를 태우면
  참여 유인이 줄어든다.
- **수수료(rake)는 패자 풀에서만.** 승자의 원금은 건드리지 않는다. 기본값은 0.
- **반올림 잔돈은 최대 스테이크 승자에게.** 총액이 정확히 보존된다
  (테스트: `test_total_is_conserved_with_awkward_ratios`).

### 스테이크를 쪼갤 수 있게 한 이유

`BUY 50 / HOLD 50`처럼 나눠 걸 수 있다. 이러면 각자의 배분이 그대로 **개인 확률
분포**가 되고, Brier score를 계산할 수 있다. "확신해서 맞힌 사람"과 "얼떨결에 맞힌
사람"이 순위표에서 구분된다.

## 안전 설계

### 자동화하지 않은 것

스케줄러(`app/scheduler.py`)는 마감, 결정 산출, 판정, 정산을 자동으로 진행한다.
**주문 승인만은 하지 않는다.** 사람이 승인 버튼을 눌러야 브로커로 나간다.

### 실계좌 이중 잠금

`brokers/factory.py`에서 `KIS_ENV=live`와 `ALLOW_LIVE_TRADING=true`가 **둘 다**
참일 때만 실전 도메인에 붙는다. 하나라도 빠지면 경고를 남기고 모의투자로 강등한다.
실수로 `KIS_ENV`만 바꿔서 실계좌로 나가는 사고를 막기 위함이다.

`orders.broker_env` 컬럼에 `paper`/`live`/`mock`을 기록해서, 나중에 주문 내역을
볼 때 모의와 실전을 헷갈릴 수 없게 했다.

### 리스크 가드

`services/risk.py`의 `check_order`가 유일한 관문이다. 새 규칙은 여기에 추가한다.
현재: 킬 스위치, 1회 주문금액, 24시간 주문 건수, 매도 시 보유수량, 매수 시 현금,
단일 종목 비중.

**잔고 조회가 실패하면 주문을 차단한다.** 검사를 건너뛰지 않는다 — 잔고를 모르는
상태로 주문을 내는 것이 조회 실패보다 위험하다.

### 정산 멱등성

`ledger_service.has_entry`로 `(회원, 마켓, 항목종류)` 조합을 확인한다. 정산이
중간에 실패해서 재실행되더라도 중복 지급되지 않는다.
`BET_REFUND`(배분 변경 시 되돌림)와 `CANCEL_REFUND`(마켓 무효)를 다른 항목으로
분리한 것도 이 체크를 정확하게 유지하기 위해서다.

## KIS 어댑터

`brokers/base.py`의 `Broker` Protocol이 계약이다: `get_quote`, `place_order`,
`get_balance` 세 개.

- `MockBroker` — 네트워크 없이 체결 시뮬레이션. 개발/테스트 기본값.
- `KISBroker` — 실제 KIS Open API.

`KISClient`가 인증/전송/에러 변환을 맡는다. 주의할 점 둘:

1. **접근토큰 발급에 유량 제한이 있다.** 메모리 + 파일 양쪽에 캐싱한다
   (`KIS_TOKEN_CACHE_PATH`). 개발 중 서버를 자주 재시작해도 재발급하지 않는다.
2. **HTTP 200이어도 실패일 수 있다.** KIS는 `rt_cd` 필드로 거절을 알린다.
   `_raise_for_rt_cd`가 이를 `BrokerError`로 변환한다.

`tr_id` 값은 `constants.py`에 모아뒀고 `KIS_TR_ID_*` 환경변수로 덮어쓸 수 있다.
KIS가 거래ID를 개편해도 코드 배포 없이 대응하기 위함이다.

## 시간 처리

`app/db/types.py`의 `UTCDateTime`이 모든 시각 컬럼을 tz-aware UTC로 통일한다.
SQLite는 타임존을 저장하지 못해서 naive datetime을 돌려주는데, 그대로 두면
`market.closes_at <= datetime.now(UTC)` 같은 비교가 테스트(SQLite)에서만 터진다.
경계에서 통일해 서비스 코드가 DB 종류를 신경 쓰지 않게 했다.

저장은 항상 UTC, 표시는 프론트엔드에서 `toLocaleString('ko-KR')`로 한국 시간.

## 다음에 손댈 만한 곳

우선순위 순으로:

1. **체결 상태 폴링** — 지금은 주문 접수(`SUBMITTED`)까지만 기록한다. KIS 주문체결
   조회 API로 체결 수량/평균가를 채우고 `positions`를 갱신하는 잡이 필요하다.
   `execution.sync_positions`가 잔고 기준 동기화를 이미 하고 있으니, 이를 주기적으로
   호출하는 것이 가장 짧은 경로다.
2. **알림** — 마켓 개설/마감 임박/정산 결과를 슬랙이나 카카오톡으로. 9명이 웹을
   주기적으로 확인하리라 기대하기 어렵다. 참여율이 곧 정족수라 알림이 곧 서비스 품질이다.
3. **영업일 계산** — `resolve_at`을 지금은 달력 날짜로 잡는다. 휴장일을 넘기면 판정가가
   직전 종가가 된다. KRX 영업일 캘린더가 필요하다.
4. **종목 검색** — 티커를 직접 입력해야 한다. KIS 종목 마스터를 받아 자동완성을 붙이면
   마켓 개설이 훨씬 쉬워진다.
5. **감사 로그** — 누가 언제 무엇을 승인했는지는 `trade_decisions.approved_by`에만
   남는다. 설정 변경(한도 조정, 킬 스위치)까지 남기려면 별도 테이블이 필요하다.
6. **부분 청산** — 매도는 현재 보유 전량이다. 비중 조절식 매도를 원하면
   `market_service.build_decision`의 SELL 분기를 고친다.
7. **마켓 유형 확장** — 지금은 `BUY/SELL/HOLD` 3지선다 고정이다. "목표가 도달 여부"
   같은 이진 마켓을 넣으려면 `Outcome` enum과 `resolve_outcome`을 마켓 유형별로
   분리해야 한다.
