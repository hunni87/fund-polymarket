# 아키텍처

계속 고쳐가며 쓸 것을 전제로 잡았다. 이 문서는 "왜 이렇게 했는지"와 "다음에 어디를
건드리면 되는지"를 남긴다.

## 레이어

```
API (FastAPI)          HTTP 경계. 권한 확인, 스키마 검증, 커밋.
  └ services/          비즈니스 규칙. DB 세션은 받지만 HTTP는 모른다.
      └ brokers/       증권사 어댑터. Protocol 하나로 추상화.
  └ models/            SQLAlchemy 테이블.
```

원칙 하나: **`services/consensus.py`는 DB도 설정도 모른다.** 확률 계산, 파리뮤추얼
정산, 판정 규칙, Brier score가 전부 순수 함수다. 돈 계산이 틀리면 안 되는 부분이라
단독으로 테스트할 수 있게 떼어놨다.

## 도메인 모델

| 테이블 | 역할 |
|---|---|
| `members` | 스터디원. `role`이 `admin`이면 운영자 액션 가능 |
| `funds` | 증권 계좌 1개 = 펀드 1개 |
| `positions` | 종목별 보유 수량. 증권사 잔고에서 동기화 |
| `markets` | 하나의 의사결정 주제. 판정 규칙과 주문 파라미터를 함께 들고 있다 |
| `bets` | `(market, member, outcome)` 당 한 행. 스테이크를 쪼개 걸 수 있다 |
| `ledger_entries` | 포인트 원장. **추가 전용** |
| `trade_decisions` | 합의 → 매매 결정. 확률 스냅샷을 함께 보관 |
| `orders` | 브로커로 나간 주문. 요청/응답 원문 포함 |

### 왜 잔고 컬럼이 없나

`members`에 `balance` 컬럼을 두지 않았다. 잔고는 항상 `ledger_entries`의 합계다.
정산 로직에 버그가 생겨도 잔고가 조용히 어긋날 수 없고, 모든 포인트 이동에 사유가
남는다. 스터디원 9명 규모에서 합계 쿼리 비용은 무시할 만하다.

부호 규약: 회원 잔고 기준이다. 베팅 잠금은 음수(`BET_LOCK`), 지급은 양수(`PAYOUT`).

### 왜 마켓 상태가 7개나 되나

`OPEN → CLOSED → DECIDED → EXECUTED → RESOLVED → SETTLED` (+ `CANCELLED`).

각 단계가 되돌릴 수 없는 부수효과와 짝지어져 있어서 합칠 수가 없다.
- `CLOSED`에서 **기준가가 확정**된다. 판정의 기준점이라 나중에 못 바꾼다.
- `EXECUTED`에서 **돈이 나간다**.
- `SETTLED`에서 **포인트가 이동한다**.

`RESOLVED`(정답 확정)와 `SETTLED`(지급)를 나눈 것은 의도적이다. 판정이 이상하면
지급 전에 사람이 확인하고 취소할 수 있어야 한다.

## 예측시장 방식: 파리뮤추얼

폴리마켓은 실제로는 CLOB(호가창) + AMM이지만, 9명짜리 스터디에는 과하다. 유동성
공급자도 없고 상시 거래도 일어나지 않는다. 그래서 **파리뮤추얼**(경마식)을 골랐다.

- 확률 = 지분 비율. 별도 가격 발견 메커니즘이 필요 없다.
- 정산 = 승자가 전체 풀을 지분대로 분배.
- 계산이 단순해서 전원이 규칙을 이해할 수 있다.

교체하고 싶다면 `services/consensus.py`의 `compute_consensus` / `settle_parimutuel`
두 함수만 바꾸면 된다. LMSR이나 시간가중 배당으로 가더라도 호출부는 그대로다.

### 정산 규칙의 디테일

- **정답에 아무도 안 걸었으면 전원 환불.** 아무도 못 맞힌 판에서 포인트를 태우면
  참여 유인이 줄어든다.
- **수수료(rake)는 패자 풀에서만.** 승자의 원금은 건드리지 않는다. 기본값은 0.
- **반올림 잔돈은 최대 스테이크 승자에게.** 총액이 정확히 보존된다
  (테스트: `test_total_is_conserved_with_awkward_ratios`).

### 스테이크를 쪼갤 수 있게 한 이유

`BUY 50 / HOLD 50`처럼 나눠 걸 수 있다. 이러면 각자의 배분이 그대로 **개인 확률
분포**가 되고, Brier score를 계산할 수 있다. "확신해서 맞힌 사람"과 "얼떨결에 맞힌
사람"이 순위표에서 구분된다.

## 안전 설계

### 자동화하지 않은 것

스케줄러(`app/scheduler.py`)는 마감, 결정 산출, 판정, 정산을 자동으로 진행한다.
**주문 승인만은 하지 않는다.** 사람이 승인 버튼을 눌러야 브로커로 나간다.

### 실계좌 이중 잠금

`brokers/factory.py`에서 `KIS_ENV=live`와 `ALLOW_LIVE_TRADING=true`가 **둘 다**
참일 때만 실전 도메인에 붙는다. 하나라도 빠지면 경고를 남기고 모의투자로 강등한다.
실수로 `KIS_ENV`만 바꿔서 실계좌로 나가는 사고를 막기 위함이다.

`orders.broker_env` 컬럼에 `paper`/`live`/`mock`을 기록해서, 나중에 주문 내역을
볼 때 모의와 실전을 헷갈릴 수 없게 했다.

### 리스크 가드

`services/risk.py`의 `check_order`가 유일한 관문이다. 새 규칙은 여기에 추가한다.
현재: 킬 스위치, 장 운영시간, 1회 주문금액, 24시간 주문 건수, 매도 시 보유수량,
매수 시 현금, 단일 종목 비중.

장 운영시간 가드(`services/market_hours.py`)는 KIS API가 어차피 거부할 주문을 미리
막는다. 중복처럼 보이지만, 거부된 주문도 `orders` 행을 남기고 일일 주문 건수 한도를
갉아먹으며 실패 원인이 로그에서 구분되지 않는다. **휴장일은 판단하지 못한다** —
주말만 거르고 최종 판단은 KIS가 한다.

**잔고 조회가 실패하면 주문을 차단한다.** 검사를 건너뛰지 않는다 — 잔고를 모르는
상태로 주문을 내는 것이 조회 실패보다 위험하다.

### 정산 멱등성

`ledger_service.has_entry`로 `(회원, 마켓, 항목종류)` 조합을 확인한다. 정산이
중간에 실패해서 재실행되더라도 중복 지급되지 않는다.
`BET_REFUND`(배분 변경 시 되돌림)와 `CANCEL_REFUND`(마켓 무효)를 다른 항목으로
분리한 것도 이 체크를 정확하게 유지하기 위해서다.

## KIS 어댑터

`brokers/base.py`의 `Broker` Protocol이 계약이다: `get_quote`, `place_order`,
`get_balance` 세 개.

- `MockBroker` — 네트워크 없이 체결 시뮬레이션. 개발/테스트 기본값.
- `KISBroker` — 실제 KIS Open API.

`KISClient`가 인증/전송/에러 변환을 맡는다. 주의할 점 둘:

1. **접근토큰 발급에 유량 제한이 있다.** 메모리 + 파일 양쪽에 캐싱한다
   (`KIS_TOKEN_CACHE_PATH`). 개발 중 서버를 자주 재시작해도 재발급하지 않는다.
2. **HTTP 200이어도 실패일 수 있다.** KIS는 `rt_cd` 필드로 거절을 알린다.
   `_raise_for_rt_cd`가 이를 `BrokerError`로 변환한다.

**거래ID는 실전 값만 관리한다.** 모의투자 값은 `to_paper_tr_id`가 규칙으로 파생한다 —
첫 글자 `T`/`J`/`C`를 `V`로 바꾸고, 시세 조회처럼 `F`로 시작하는 것은 그대로 둔다.
두 벌을 따로 들고 있으면 한쪽만 고치는 드리프트가 생기기 때문이다. 규칙의 출처는
KIS 공식 툴킷이며, 자세한 대조 내역은 [KIS-MCP.md](KIS-MCP.md)에 있다.

실전 값은 `KIS_TR_ID_*` 환경변수로 덮어쓸 수 있다. KIS가 거래ID를 개편해도 코드 배포
없이 대응하기 위함이다.

## 체결 확인

주문을 **접수시킨 것**과 **체결된 것**은 다른 사건이다. 그 사이에 부분체결, 미체결,
취소가 끼어든다. 접수 응답만 보고 "샀다"고 기록하면 장부가 조용히 어긋난다.

`services/fills.py`가 미체결 주문(`SUBMITTED`/`PARTIALLY_FILLED`)을 골라 증권사에
직접 물어보고, 답만 기록한다. 스케줄러가 매 tick마다 부르고, 관리자는
`POST /orders/sync`로 즉시 돌릴 수도 있다.

상태 판정에서 중요한 것 셋:

- **주문 수량은 우리가 낸 값을 기준으로 삼는다.** KIS 응답의 `ord_qty`가 비어 오는
  경우가 있어서, 그걸 기준으로 삼으면 미체결(0/0)을 전량 체결로 오독한다.
- **모르는 주문번호는 상태를 건드리지 않는다.** 접수 직후에는 체결 내역에 아직
  안 보일 수 있다. 조회했다는 사실(`last_synced_at`)만 남긴다.
- **환경이 다르면 조회하지 않는다.** 주문번호는 mock/모의/실전 사이에서 아무 의미가
  없다. `orders.broker_env`가 현재 브로커와 같은 것만 묻는다.

체결이 확인되면 `execution.sync_positions`를 불러 **증권사 잔고로 포지션을
덮어쓴다.** 체결 수량을 로컬에서 더하지 않는다 — 잔고가 유일한 진실이라는 원칙은
여기서도 유지된다. `orders.filled_quantity`는 그 주문 한 건이 얼마나 나갔는지를
보여주는 기록일 뿐, 보유 수량의 근거가 아니다.

한 건의 조회가 실패해도 나머지는 계속 처리하고 다음 주기에 다시 시도한다. 조회
실패 때문에 다른 주문의 체결을 놓치는 편이 더 나쁘다.

## 알림

9명이 웹을 알아서 들여다볼 것이라고 기대할 수 없다. **참여율이 곧 정족수**이고,
정족수를 못 채우면 마켓이 통째로 SKIP 된다. 그래서 알림은 부가 기능이 아니라
서비스 품질 그 자체다.

`app/notifiers/`가 채널 어댑터(브로커와 같은 구조), `services/notifications.py`가
"무엇을 알릴지"를 정한다. 알리는 사건은 넷:

| 사건 | 언제 | 왜 |
|---|---|---|
| 마켓 개설 | `POST /markets` 커밋 후 | 참여를 시작하게 |
| 마감 임박 | 스케줄러, 마감 N분 전 1회 | 미참여자를 재촉. 아직 안 낸 인원 수를 함께 보낸다 |
| 합의 결과 | `build_decision` | 승인 대기면 사람이 눌러야 한다. SKIP도 알린다 |
| 정산 완료 | `settle_market` | 결과와 수령자 수 |

설계상 지킨 것 셋:

- **웹훅 URL이 없으면 noop으로 떨어진다.** 알림 설정을 강제해서 로컬 개발을 막지
  않는다. 다만 조용히 사라지지 않고 로그에는 남는다.
- **전송 실패는 절대 위로 전파하지 않는다.** 알림이 안 갔다고 정산이 롤백되면 그게
  더 큰 사고다. `notifications._send`가 모든 예외를 삼킨다.
- **마감 임박 알림은 마켓에 보낸 시각을 기록한다**(`closing_soon_notified_at`).
  스케줄러는 1분마다 돌기 때문에, 기록하지 않으면 마감 전 한 시간 동안 60번 간다.

알고 쓸 것 하나: 알림은 **커밋 전에** 나간다(마켓 개설만 예외). 뒤이어 트랜잭션이
실패하면 "일어나지 않은 일"이 알림으로 나갈 수 있다. 9명 규모에서 이 확률과 비용이
아주 작다고 보고, 세션 이벤트를 얽는 비용을 피했다. 문제가 되면 `session_scope`의
after_commit 훅으로 옮기면 된다.

## 종목 마스터

마켓을 열 때 티커를 외워서 치게 하지 않으려면 로컬에 종목 목록이 있어야 한다.
**KIS에는 "이름으로 종목 찾기" API가 없기 때문이다** — 티커로 조회하는 것만 된다.

`symbols` 표는 두 경로로 채워진다:

1. **CSV 임포트** — `python -m scripts.import_symbols <csv>`. 상장 목록 전체를
   한 번에. KRX 정보데이터시스템에서 받은 엑셀을 `ticker,name,market` 세 컬럼으로
   저장하면 된다.
2. **시세 조회** — 관리자가 마켓 개설 화면에서 티커를 확인할 때마다, 증권사가 준
   정식 이름이 마스터에 반영된다. 임포트한 이름이 낡았어도 여기서 교정된다.

즉 **임포트하지 않아도 서비스는 돌아간다.** 쓸수록 채워지고, 처음 한 번만 티커를
알면 된다.

관련해서 `MockBroker`는 **모르는 종목의 이름을 지어내지 않는다.** 예전에는
`MOCK-005930` 같은 문자열을 돌려줬는데, 그러면 개발 중 시세 조회 한 번에 종목
마스터의 "삼성전자"가 그 문자열로 덮어써진다. 모의 데이터가 마스터를 오염시키는
경로는 막아둔다.

상장폐지 종목은 지우지 않고 `is_active=false`로 감춘다. 지난 마켓이 그 티커를
참조하고 있을 수 있다.

## 시간 처리

`app/db/types.py`의 `UTCDateTime`이 모든 시각 컬럼을 tz-aware UTC로 통일한다.
SQLite는 타임존을 저장하지 못해서 naive datetime을 돌려주는데, 그대로 두면
`market.closes_at <= datetime.now(UTC)` 같은 비교가 테스트(SQLite)에서만 터진다.
경계에서 통일해 서비스 코드가 DB 종류를 신경 쓰지 않게 했다.

저장은 항상 UTC, 표시는 프론트엔드에서 `toLocaleString('ko-KR')`로 한국 시간.

## 다음에 손댈 만한 곳

우선순위 순으로:

1. **영업일/휴장일 캘린더** — `resolve_at`을 지금은 달력 날짜로 잡는다. 휴장일을 넘기면
   판정가가 직전 종가가 된다. `services/market_hours.py`도 주말만 거르고 공휴일은
   모른다. KRX 영업일 캘린더 하나로 두 문제가 같이 풀린다.
2. **감사 로그** — 누가 언제 무엇을 승인했는지는 `trade_decisions.approved_by`에만
   남는다. 설정 변경(한도 조정, 킬 스위치)까지 남기려면 별도 테이블이 필요하다.
3. **부분 청산** — 매도는 현재 보유 전량이다. 비중 조절식 매도를 원하면
   `market_service.build_decision`의 SELL 분기를 고친다.
4. **마켓 유형 확장** — 지금은 `BUY/SELL/HOLD` 3지선다 고정이다. "목표가 도달 여부"
   같은 이진 마켓을 넣으려면 `Outcome` enum과 `resolve_outcome`을 마켓 유형별로
   분리해야 한다.
